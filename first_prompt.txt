## 0. Product Snapshot

**Name:** PrepIntel
**Tagline:** "Know What Companies Ask. Prepare Smarter."
**One-liner:** A placement-intelligence platform that turns noisy OA/interview reports into uncertainty-aware, personalized question recommendations, using the Bayesian scoring engine defined in the math spec.

**Reference design (from screenshot):**
- Eye logo (gradient cyan→violet, iris-in-eye mark), wordmark "Prep**Intel**" (Prep in white, Intel in gradient)
- Landing page: dark navy/black background (`#05060A`–`#0B0D14` range), large hero headline, gradient CTA button (violet→cyan), trust logos row, 4 feature bullets with icon chips, floating 3D "eye + bar chart" hero graphic with orbiting pill labels ("Real Data", "Smart Analysis", "Crack Placements")
- App shell: fixed left sidebar (icon+label nav: Overview, Analytics, Questions, Reports, Roadmap, Bookmarks, Progress), top bar with global search + Company/Role/Year dropdown selectors
- Dashboard: topic-frequency stat cards (icon chip, topic name, %, trend arrow ↑/↓ in green/red), line chart card ("Topic Trend — Last 12 Months") with multi-series colored lines, donut chart card ("Difficulty Distribution"), "Top Recommended Questions" ranked list with tag pills + score badge, "N-Day Preparation Plan" week-by-week progress bars, a "Confidence Score" badge top-right (colored dot + X/100), and a Pro-plan upsell card in sidebar footer with user profile chip
- Visual language: glassmorphic cards (subtle border, low-opacity fill, soft shadow), rounded-2xl corners, gradient accents used sparingly (CTA, logo, active nav item, headline highlight word), green/amber/red used only for semantic states (up/down/difficulty), everything else neutral dark/gray/white

This is the target aesthetic for **every** screen you build in every phase — dense, data-forward, "command-center" styling, consistent with the rest of Prince's project portfolio.

**Stack (matches CodePilot precedent — reuse for consistency and free-tier hosting):**
- Frontend: Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui + Framer Motion + Recharts (or visx) for charts
- Backend: FastAPI (Python) for the math/scoring engine + ingestion pipeline; Next.js API routes / route handlers for thin CRUD where FastAPI isn't needed
- DB: PostgreSQL (Supabase) — relational core + Row Level Security for multi-user data (bookmarks, progress, skill profile)
- Cache/Queue: Upstash Redis (caching precomputed analytics, rate limiting) + a background job runner (Celery, or simple cron via Railway/Render if avoiding Celery for MVP)
- Auth: Supabase Auth (email + OAuth)
- Hosting: Vercel (frontend) + Railway (FastAPI worker + Postgres if not using Supabase) — zero-cost tier via GitHub Student Pack, same as CodePilot
- Charts: Recharts for line/donut (matches reference image chart style)

## Phase 2 — Data Model & Ingestion Schema

**Goal:** Design the Postgres schema that the math engine (Phase 4) will read/write, and the ingestion pipeline that turns raw reports into structured observations.

**Prompt to use:**

```
Design a PostgreSQL schema (with Supabase RLS policies) for PrepIntel covering:

Core entities:
- companies (id, name, slug, logo_url, category)
- roles (id, name, slug) e.g. "SDE Intern", "SDE-1"
- recruitment_cycles (id, year, label)
- rounds (id, name) e.g. "OA", "Technical 1", "HR"
- topics (id, name, slug, parent_topic_id nullable) — supports the hierarchy from the math spec (DP -> 1D DP -> Coin Change)
- questions (id, canonical_title, slug, topics[] via join table, difficulty_label, estimated_time_minutes, external_links jsonb)

Observation pipeline:
- raw_reports (id, source_type enum['user_submission','scraped_public','screenshot_ocr','manual_admin'], source_url, raw_text, submitted_by_user_id nullable, company_id, role_id, round_id, cycle_id, submitted_at, status enum['pending','processed','rejected','duplicate'])
- report_topic_observations (id, raw_report_id, topic_id, present boolean, extraction_confidence float) — this is the X_ij matrix from the math spec, one row per (report, topic)
- report_question_observations (id, raw_report_id, question_id nullable, question_text_raw, matched_confidence float) — for direct-evidence tracking
- source_reliability_scores (source_type, reliability_weight float, last_calibrated_at) — matches w_s(i) in the spec
- duplicate_clusters (id, cluster_method, created_at) + raw_report_id FK — for the independence adjustment (I_i) from section 13

Precomputed analytics (written by the batch job in Phase 4, read by the API):
- topic_scores (company_id, role_id, round_id, cycle_id, topic_id, raw_count, weighted_count, raw_frequency, weighted_probability, posterior_mean, credible_interval_low, credible_interval_high, effective_sample_size, recency_score, trend_score, confidence_score, generated_at) — exactly matching section 32 of the math spec
- question_scores (company_id, role_id, cycle_id, question_id, topic_score, pattern_score, direct_evidence_score, difficulty_score, recency_score, diversity_score, final_recommendation_score, generated_at)
- difficulty_distributions (company_id, role_id, round_id, cycle_id, easy_pct, medium_pct, hard_pct)

User-facing state:
- user_skill_profile (user_id, topic_id, skill_level enum['weak','medium','strong'], updated_at)
- bookmarks (user_id, question_id, created_at)
- user_progress (user_id, question_id, status enum['not_started','attempted','solved'], updated_at)
- prep_plans (user_id, company_id, role_id, total_days, generated_at) + prep_plan_days (plan_id, day_number, topics[], target_completion_pct)

Write this as a single SQL migration file with proper foreign keys, indexes on the (company_id, role_id, round_id, cycle_id) lookup pattern used constantly by the dashboard, and RLS policies so users only see their own bookmarks/progress/skill_profile/prep_plans but can read all topic_scores/question_scores (public analytics).
```

**Definition of Done:** Migration runs clean on a fresh Supabase project; you can manually insert a raw_report + observations and query them back.

## Phase 4 — MVP Math Engine (Backend, FastAPI)

**Goal:** Implement exactly the "MVP" checklist from the math spec (section 34) as a batch job, not real-time computation.

**Prompt to use:**

```
Build a FastAPI service ("prepintel-engine") that runs as a scheduled batch job (cron or Celery beat, every N hours) implementing the MVP math pipeline from the attached spec:

1. Ingest new raw_reports with status='pending' -> run topic extraction (start with keyword/regex matching against topics.slug + synonyms table; leave an LLM-based extractor as a swappable interface for Phase 2/3) -> write report_topic_observations -> mark report processed

2. Deduplication (section 12-13): cluster raw_reports by (company_id, role_id, round_id, cycle_id) + text similarity (start with a simple trigram/cosine similarity on raw_text via pg_trgm; assign independence_factor I_i: 1.0 unclustered, 0.3 likely-duplicate, 0.0 exact-duplicate)

3. Recency weighting (section 6): w_r(t) = exp(-lambda * age_in_days/365), lambda configurable via env var, default such that a 1-year-old report ≈ 0.70 weight (solve for lambda from that anchor)

4. Source weighting (section 7): pull from source_reliability_scores table

5. Combined weight (section 8): w_i = w_s(i) * w_r(t_i) * I_i

6. Weighted frequency + Beta-Binomial posterior (section 9): for each (company, role, round, cycle, topic), compute weighted successes/failures, posterior = Beta(alpha_prior + s, beta_prior + f) with alpha_prior=beta_prior=1 (uniform prior) as default, expose as configurable

7. Effective sample size (section 11): N_eff = (sum w_i)^2 / sum(w_i^2)

8. Confidence score: derive a 0-100 confidence_score from N_eff (e.g. logistic/sigmoid mapping so N_eff=1 -> low, N_eff>=15 -> high; make the mapping function a named, testable unit) — this feeds the <ConfidenceBadge /> in the UI

9. Trend score (section 17-18): compute EMA over monthly buckets, trend_score = p_recent - p_historical, classify as Increasing/Stable/Decreasing with a configurable threshold

10. Write all results to topic_scores table per section 32's exact column list

11. Question scoring (sections 23-25, MVP subset only — skip embeddings for now): 
    Score(q) = w1*topic_score + w2*pattern_score(keyword-overlap only, not embeddings) + w3*recency + w4*difficulty_fit + w5*direct_evidence_score
    normalize to 0-100, write to question_scores

12. Difficulty distribution (section 20): simple weighted proportion of easy/medium/hard per (company,role,round,cycle), write to difficulty_distributions

Expose read-only REST endpoints for the frontend:
GET /api/topics?company=&role=&cycle=  -> topic_scores rows, sorted by weighted_probability desc
GET /api/questions?company=&role=&cycle=&limit=  -> question_scores joined with questions, sorted by final_recommendation_score desc
GET /api/difficulty?company=&role=&round=&cycle=
GET /api/trend?company=&role=&topic=&months=12  -> monthly time series for the chart

Every response must include the underlying components (not just the final number) so the frontend can render the "Why?" breakdown from section 31 later.

Write this with clear separation: ingestion.py, weighting.py, bayesian.py, dedup.py, scoring.py, trend.py — each independently unit-testable with synthetic report data.
```

**Definition of Done:** Seed 50-100 synthetic raw_reports across 2-3 companies/topics, run the batch job, and confirm topic_scores/question_scores populate with sane numbers (spot-check the Beta-Binomial math against the worked examples in the spec, e.g. section 10's "2/2 reports -> high estimate, low confidence").

## Phase 8 — Preparation Plan Generator (Knapsack Optimizer)

**Goal:** Implement spec sections 27-28 (time-constrained optimization + diversity constraint) to generate the "N-Day Preparation Plan" panel for real.

**Prompt to use:**

```
Build a /roadmap page and wire the dashboard's "N-Day Preparation Plan" panel to it:

Backend: given available_hours (user input, default derived from N days * hours/day setting) and the current question_scores set, solve the knapsack-style selection from section 27:
maximize sum(Value(q) * x_q) subject to sum(Time(q) * x_q) <= T, x_q in {0,1}
Value(q) = final_recommendation_score (optionally personalized from Phase 7), Time(q) = estimated_time_minutes.
Use a simple DP knapsack (question counts will be small, <500, so this is cheap) — implement in Python, expose as POST /api/prep-plan.

Apply the diversity penalty from section 28: after initial knapsack selection, if more than ~40% of selected questions share the same primary topic, apply FinalValue(q) = Value(q) - lambda * SimilarityToSelected(q) (similarity = shared topic overlap ratio) and re-solve, or use a simpler greedy diversity re-rank for MVP — document which approach you chose.

Group the output into week-buckets (day 1-5, 6-10, 11-15...) with a topic summary per week and a target completion % (matches the reference screenshot's "Week 1 (Days 1-5): Arrays, Hashing, Sliding Window — 80%" style rows with a horizontal progress bar per week).

Frontend: /roadmap page shows the full multi-week breakdown; dashboard panel shows a condensed 3-week preview + "View Full Roadmap →".

Persist the generated plan to prep_plans/prep_plan_days so it doesn't regenerate on every page load; add a "Regenerate" button.
```

**Definition of Done:** Entering a target day-count and hours/day produces a week-by-week plan that respects the time budget and isn't dominated by one topic.

## Phase Ordering Rationale

Phases 1→3 get you a demo-able shell fast (good for early feedback/screenshots). Phase 4 is the highest-risk, most novel piece (the math spec) — building it in isolation with synthetic data (Phase 4) before wiring the UI (Phase 5) means you can validate the Bayesian math against the spec's worked examples without also debugging frontend state at the same time. Phases 6-9 layer product depth on a now-proven data pipeline. Phase 10 is the "make it defensible in an interview/demo" pass — matches the same iterative-UI-audit pattern you used on the Hospital Command Center and CodePilot dashboards.

## What to explicitly defer (per spec section 34, Phase 2/3 items)

Do NOT build these until the MVP above is live and validated against real data: hierarchical Bayesian borrowing-strength across company/role groups (section 16), semantic embeddings for pattern similarity (section 25), change-point detection (section 19), logistic-regression calibration, automated source-reliability learning. Building these before you have real observation volume is over-engineering against synthetic assumptions.
